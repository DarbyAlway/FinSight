# เตรียมสัมภาษณ์ — FinSight (Multi-Agent Financial Research Assistant)

คำตอบด้านล่างอ้างอิงจากโค้ดจริง (มี file:line กำกับ) เพื่อให้พูดได้แบบเจาะจง ไม่ใช่ทฤษฎี
LangGraph ทั่วไป แต่ละคำถามมี:
- **คำตอบที่พูดออกเสียง** — สิ่งที่ควรพูด ~45–90 วินาที เป็นประโยคง่าย ๆ
- **ถ้าถูกซักต่อ / รายละเอียดสำรอง** — รายละเอียดเชิงเทคนิคที่ลึกกว่า เผื่อโดนถามต่อ

## สัมภาษณ์แค่ 30 นาที — อ่านส่วนนี้ก่อนทุกครั้ง

คุณจะพูดไม่ทันเนื้อหาทั้งหมดด้านล่างแน่นอน การพยายามพูดให้ครบจะเสียเวลามากกว่าการข้ามบางส่วนไป —
การพูดยืดยาวจะกินเวลาที่ควรเหลือไว้สำหรับคำถามตามที่แสดงให้เห็นว่าเราเข้าใจจริง งบเวลาที่สมจริง:
คำถามจะถูกถามจริง ๆ แค่ **3-5 ข้อ** ไม่ใช่ทั้งหมดในลิสต์

**งบเวลา:** 0-3 นาที แนะนำตัว → 3-5 นาที "เล่าให้ฟังเกี่ยวกับโปรเจกต์" (ด้านล่าง) → 5-22 นาที
คำถามเชิงเทคนิค (3-5 ข้อ) → 22-28 นาที คำถามเพิ่มเติมหรือแบบฝึกหัด → 27-30 นาที "มีคำถามอะไรจะ
ถามเราไหม" (**เลือกแค่ 1 ข้อ** ดู Section 6)

**คำเปิด 65 วินาที — ต้องพูดได้คล่องโดยไม่ต้องดูโน้ต:**
"FinSight เป็นผู้ช่วยวิจัยการเงินแบบ multi-agent คุณถามคำถามเกี่ยวกับหุ้นเป็นภาษาธรรมดา แทนที่
โมเดลตัวเดียวจะตอบจากความจำ มันจะวางแผนงาน กระจายงานให้ specialist agent สี่ตัวทำงานพร้อมกัน
เพื่อดึงข้อมูลจริงจาก SEC filings และข้อมูลตลาด แล้วสังเคราะห์คำตอบจากสิ่งที่ดึงมาได้จริงเท่านั้น
ส่วนที่ผมภูมิใจที่สุด: ก่อนที่คุณจะเห็นคำตอบนั้น มี deterministic verifier — ไม่ใช่ LLM ตัดสิน LLM
— ตรวจทุกตัวเลขในคำตอบเทียบกับข้อมูลที่ดึงมาจริง ให้ตรงปีด้วย ถ้ามีตัวเลขที่สืบย้อนกลับไม่ได้
มันจะถูกเขียนใหม่ ถูกยกระดับไปค้นเว็บสด ๆ หรือคำตอบจะบอกตรง ๆ ว่ายืนยันตัวเลขนี้ไม่ได้ ระบบนี้
สร้างด้วย LangGraph state graph ที่กระจายงานแบบขนานและมี checkpointing กู้คืนได้เมื่อระบบล่ม
ผ่านการทดสอบ 305 เทสต์ที่รันกับข้อมูล SEC จริง ไม่ใช่ mock"

**ลำดับความสำคัญ:**
- **Tier 1 — ต้องคล่องแบบไม่ต้องดูโน้ต:** คำเปิดด้านบน · ระบบ fidelity (จุดเด่นที่สุดของคุณ —
  โยงมาตรงนี้ทุกครั้งที่คำถามเปิดโอกาสให้ทำได้) · ทำไมต้อง multi-agent (Section 5 Q5) ·
  **ตัวเลข 24× และการ deploy แบบ full-stack ด้านล่าง — สองอย่างนี้อยู่ใน CV ตรงตัว
  ผู้สัมภาษณ์อ่านมาแล้วแน่นอน ให้ถือว่าเกือบจะถูกถามแน่**
- **Tier 2 — เตรียมเวอร์ชันย่อ 20-30 วินาที ไม่ต้องพูดนำ:** guardrails/robustness
  (รวม Q2+Q3 เข้าด้วยกัน) · การประเมินผล (Q4) · ทำไมต้อง LangGraph (Q6 — ตอบเฉพาะถ้าถูกถาม
  "ทำไมเลือกสแตกนี้") · เรื่อง ticker resolution ด้านล่าง
- **Tier 3 — อ่านผ่าน ๆ ตอนเช้าก่อนสัมภาษณ์ ไม่ต้องซ้อม:** รายละเอียดเชิงลึกของ fidelity แบบทีละ
  บรรทัด, ส่วน "จุดอ่อนที่ควรยอมรับตรง ๆ", ความต่างระหว่าง LangChain กับ LangGraph

## คำถามเปิด — "เล่าเกี่ยวกับตัวเอง" / จุดแข็ง / จุดอ่อน

คำถามพวกนี้จะมาใน 0-3 นาทีแรก ก่อนเนื้อหาเทคนิคใด ๆ ตอบไม่ดีตรงนี้จะตั้งกรอบที่ไม่ดีก่อนที่คุณ
จะได้ไปถึงส่วนที่คุณแข็งจริง ๆ

### "เล่าเกี่ยวกับตัวเองให้ฟังหน่อย"

**ต้องกรอกส่วนในวงเล็บเองด้วยข้อมูลจริงของคุณ** — นี่คือจุดเดียวในเอกสารนี้ที่คุณรู้ข้อเท็จจริง
แต่เอกสารนี้ไม่รู้ อย่าปล่อยว่างหรือเดาสด ๆ ตอนสัมภาษณ์

**โครงคำตอบที่พูดออกเสียง (~45-60 วิ) แบบ อดีต → ปัจจุบัน → อนาคต:**
"[สถานะ/บทบาทปัจจุบันของคุณ — เช่น 'ตอนนี้ผมเป็นนักศึกษาปีสุดท้ายที่ ___' หรือ 'ตอนนี้ผมทำงาน
เป็น ___ ที่ ___'] ในช่วง [ระยะเวลา] ที่ผ่านมา ผมสร้างประสบการณ์ตรงกับระบบ AI agent มาเรื่อย ๆ
— ล่าสุดคือผู้ช่วยวิจัยการเงินแบบ multi-agent ที่วางแผนคำถาม กระจายงานให้ specialist agent
สี่ตัวทำงานพร้อมกันเพื่อดึงข้อมูลจริงจาก SEC filings และข้อมูลตลาด และ — ส่วนที่ผมภูมิใจที่สุด —
ตรวจทุกตัวเลขในคำตอบสุดท้ายเทียบกับข้อมูลที่ดึงมาจริงก่อนส่งออกไป เพราะผมอยากแก้ปัญหา
hallucination จริง ๆ ไม่ใช่แค่สร้าง chatbot wrapper อีกตัว นอกจากนี้ผมยังดูแล pipeline เล็ก ๆ
ให้ทีมของผม ที่ขยาย QA dataset ที่มีข้อมูลน้อยเกินไป โดยใช้ retrieval บวกกับ LLM-as-judge filter
แทนการ label มือ สิ่งที่เชื่อมสองอย่างนี้เข้าด้วยกันคือความคิดแบบเดียวกัน: ไม่ใช่แค่เรียก LLM
แต่สร้าง deterministic check และสถาปัตยกรรมรอบ ๆ มันเพื่อให้ผลลัพธ์เชื่อถือได้จริง นี่คือสิ่งที่
ทำให้ผมสนใจตำแหน่ง AI Agent Developer — ผมอยากสร้างระบบแบบนี้ใน production ต่อไป ไม่ใช่แค่ทำ
prototype"

**ถ้าถูกถามต่อ "ทำไมถึงมองหางานตอนนี้":** [PLACEHOLDER — กรอกเหตุผลจริงของคุณ อย่าเดาสด ๆ
ตอนสัมภาษณ์ เพราะนี่คือสิ่งที่ผู้สัมภาษณ์ถามต่อได้ง่ายที่สุด]

### "จุดแข็งที่สุดของคุณคืออะไร"

**คำตอบที่พูดออกเสียง (~30-40 วิ):**
"ผมไม่เชื่อผลลัพธ์ของ LLM แบบเปล่า ๆ ในจุดที่คำตอบผิดจะสร้างความเสียหายจริง — ผมจะสร้าง
deterministic check รอบมันแทนที่จะหวังว่าโมเดลจะตอบถูก ตัวอย่างที่ชัดที่สุดคือ fidelity
verifier ในผู้ช่วยการเงินของผม: ทุกตัวเลขในคำตอบสุดท้ายจะถูกสืบย้อนกลับไปยังข้อมูลที่ดึงมาจริง
โดยไม่มี LLM ตัดสิน LLM เลย ความคิดแบบเดียวกันนี้ก็ปรากฏในวิธีที่ผมตัดสินใจเรื่อง performance —
ตอนที่ผมลดเวลาคำถามจาก 167 วินาที เหลือประมาณ 7 วินาที ผมไม่ได้เดาว่าส่วนไหนช้า ผมจับเวลาทุกรอบ
ทั้งก่อนและหลัง แล้วเลือกทางแก้จากตัวเลขจริง ไม่ใช่ความรู้สึก ผมอยากส่งมอบสิ่งที่ผมยืนยันได้ด้วย
หลักฐาน มากกว่าสิ่งที่ดูน่าประทับใจจนกว่าจะมีคนถามว่า 'รู้ได้ยังไงว่ามันถูก'"

### "จุดอ่อนของคุณคืออะไร"

**คำตอบที่พูดออกเสียง (~30-40 วิ):**
"ผมมักจะสร้างส่วนที่ยากและน่าสนใจของระบบก่อน แล้วค่อยกลับมาทำความแข็งแรงเชิง operational
ทีหลัง ในผู้ช่วยการเงินของผม ผมสร้าง pipeline ตรวจจับ hallucination ที่ค่อนข้างซับซ้อน แต่ยัง
ไม่มี retry-with-backoff หรือ rate limiting กับการเรียก SEC EDGAR หรือ yfinance จริง ๆ เลย —
ถ้าตัวไหนโดน rate limit หรือ timeout การเรียกนั้นก็แค่ fail ไม่ได้ retry อย่างนุ่มนวล ผมรู้ชัดเจน
ว่าขาดอะไรและจะสร้างมันยังไง — token-bucket rate limiter, exponential backoff แบบมี jitter —
แค่ยังไม่ได้ลงมือทำเพราะปัญหาเรื่องความถูกต้องดึงความสนใจผมมากกว่าปัญหาเรื่อง resilience ผม
พยายามฝึกตัวเองให้มอง operational robustness เป็นส่วนหนึ่งของ 'เสร็จ' ตั้งแต่ต้น ไม่ใช่สิ่งที่
ค่อยย้อนกลับมาทำทีหลัง"

**ทำไมคำตอบนี้ใช้ได้ผล:** มันเป็นเรื่องจริง (ตรวจสอบกับโค้ดจริงในเซสชันเตรียมตัวนี้แล้ว ไม่ได้
คิดขึ้นมาสำหรับสัมภาษณ์) เจาะจง และมีทางแก้ที่ชัดเจนต่อท้าย — ไม่ใช่ humble-brag แอบแฝง ("ผมทำงาน
หนักเกินไป") ซึ่งผู้สัมภาษณ์ได้ยินบ่อยจนไม่เชื่อทันที

## จุดใน CV ที่ผู้สัมภาษณ์อ่านมาแล้ว — ต้องเตรียมให้พร้อม

สามข้อนี้อยู่ใน CV ตรงตัว และ **ไม่ได้อยู่ในชุดคำถามที่คุณได้รับมา** — นั่นทำให้มันเสี่ยงกว่ารายการ
ที่เตรียมไว้แล้ว ไม่ใช่เสี่ยงน้อยกว่า เพราะยังไม่มีสคริปต์ที่ขัดเกลาแล้ว และมันเป็นสิ่งที่ผู้สัมภาษณ์
เห็นตรงหน้าและถามได้ง่ายที่สุด

### "เล่าเรื่องความเร็วที่เพิ่มขึ้น ~24× ให้ฟังหน่อย" (CV: "~24× faster responses through smart model routing")

**คำตอบที่พูดออกเสียง (~35 วิ):**
"ตัวเลขนี้วัดจริง ไม่ใช่ปัดตัวเลขเอาสวย ๆ — คำถามแบบ ticker เดียวใช้เวลาจาก 167 วินาที เหลือแค่
ประมาณ 7 วินาที เดิมที specialist agent รันอยู่บนโมเดลแบบ reasoning ซึ่ง hidden chain-of-thought
ทำให้แต่ละรอบของ tool-call ใช้เวลา 8 ถึง 57 วินาที กรณีแย่ที่สุดคำถามเดียวใช้เวลา 167 วินาที
ผมเปลี่ยน agent ทั้งสี่ตัวไปใช้โมเดลเล็กลงที่ไม่ใช่ reasoning model ซึ่งเร็วและแม่นยำเรื่อง
tool-calling โดยเฉพาะ — ประมาณ 1.4 วินาทีต่อรอบ — และแยกโมเดลอีกตัวไว้สำหรับ planning กับ
synthesis เพราะสองงานนี้ไม่ต้องใช้ tools เลย ใช้ reasoning model ก็เกินความจำเป็น ผมยังทำให้
tool call ภายในรอบเดียวกันรันพร้อมกันแทนที่จะรันทีละตัว เพราะมันเป็นแค่ network I/O รวมกันแล้ว
ทำให้กรณีแย่ที่สุดจาก 167 วินาที เหลือประมาณ 7 วินาที — และผมยืนยันแล้วว่าไม่ใช่การแลกความเร็ว
กับความแม่นยำ: ตัว fidelity checker ยังแสดงผล hard mismatch เป็นศูนย์หลังเปลี่ยน"

**ถ้าถูกถามต่อ — "วัดยังไงกันแน่?":**
"ผมจับเวลาคำถามจริงทั้งก่อนและหลังเปลี่ยนโมเดลโดยตรง — ไม่ใช่ synthetic benchmark คำถามแบบ
ticker เดียวไป 167s→~7s คำถามเปรียบเทียบหลายบริษัทอยู่ที่ประมาณ 8 วินาที คำถามเน้น ratio
ประมาณ 5 วินาที มันอยู่ใน commit message ตอนที่ผมทำการเปลี่ยนแปลงนี้ พร้อมเหตุผลของแต่ละ
โมเดลที่เลือก"

### "เล่าเรื่องการ deploy แบบ full-stack ให้ฟังหน่อย" (CV: "FastAPI backend streaming live results to a React chat interface, with secure login, saved chat history")

**คำตอบที่พูดออกเสียง (~45 วิ):**
"Backend เป็น FastAPI, frontend เป็น React กับ TypeScript ส่วนที่น่าพูดถึงจริง ๆ คือ: ตัว
orchestrator เองเป็น blocking call — รัน LangGraph หนึ่งเทิร์นเต็ม ๆ — ผมเลยรันมันบน

## Cheat sheet — ตัวเลขที่ต้องนึกออกทันที

- **LangGraph `StateGraph` 11 โหนด**: plan → gates → agent (ขนานผ่าน `Send`) → collect →
  [proactive_web] → synthesize → [web_fallback] → [fidelity_check] → [self_critique] →
  [web_escalate] → finalize (`orchestrator.py:449-476`)
- **specialist agent 4 ตัว**: financials, news, calc, ratios (`agents/`) แต่ละตัวมี tool list
  ของตัวเองและใช้ guarded tool-calling loop ร่วมกัน (`agents/_tooling.py`)
- **Guardrails** บน tool loop ของทุก agent: จำกัดสูงสุด 8 รอบของ tool-call, งบ token 30k,
  หยุดหลังได้ผลลัพธ์ error/no-data ติดกัน 3 ครั้ง, มี cache กันเรียกซ้ำ (`agents/_tooling.py:16-18`)
- **Deterministic fidelity verifier**: ดึงตัวเลขที่มีหน่วยทุกตัวออกจากคำตอบด้วย regex ผูกกับ
  ปีงบการเงิน แล้วเช็คกับ raw tool output ที่ tolerance ±1% ไม่มี LLM ตัดสิน LLM
  (`tools/fidelity.py`)
- **เทสต์ pytest 305 ตัว** นโยบายใช้ข้อมูลจริง (ยิงเข้า SEC EDGAR จริง ไม่ใช่ fixture สังเคราะห์)
  ความล้มเหลวจริงจะถูกบันทึกใน `tests/failure_log.jsonl` แล้วกลายเป็น regression test ที่ตรึงไว้
- **Checkpointing**: Postgres ตอน production (ตั้งค่า `DATABASE_URL`), SQLite ตอน
  offline/test — resume ได้เมื่อระบบล่มกลางเทิร์นโดยไม่ต้องรันโหนดที่เสร็จแล้วซ้ำ (`tools/pg.py`)
- **การเลือกโมเดลไม่ใช่แบบ one-size-fits-all**: planner/synthesis =
  `Meta-Llama-3.3-70B-Instruct` (JSON แม่นยำ ไม่มี tools ~1-2s); agents = `gemma-4-31B-it`
  (ไม่ใช่ reasoning ~1.4s/รอบ เรียก tool แบบขนานได้แม่นยำ — `gpt-oss-120b` แบบ reasoning ใช้เวลา
  8-57s แปรผัน และ Llama-3.3 ขึ้น 400 error ตอน tool call ปริมาณมากบน SambaNova)
  (`tools/config.py:21-24`)
- **Offline eval harness** (`eval_models.py`): เทียบสองโมเดลแบบตัวต่อตัวในเรื่องความแม่นยำของ
  plan routing (10 เคส) และการเลือก tool (10 เคส) แล้ว dump ผลลง `eval_results.json`
- **Observability**: self-hosted Langfuse v3, หนึ่ง trace ต่อหนึ่งเทิร์นแบบซ้อนกัน, จำนวน
  fidelity mismatch ถูกส่งออกเป็น trace score — อัตรา hallucination จึงเป็นตัวชี้วัดที่ติดตามได้
  จริง ไม่ใช่ความรู้สึก

# Section 5 — คำถามฝึกสัมภาษณ์

## 1. "เล่าสถาปัตยกรรมของ multi-agent financial assistant ตั้งแต่ user input จนถึงคำตอบสุดท้ายให้ฟังหน่อย"

**คำตอบที่พูดออกเสียง:**
"มันคือ LangGraph `StateGraph` ที่มี 11 โหนด เมื่อคำถามของผู้ใช้เข้ามา โหนดแรกคือ **planner**
LLM — temperature ต่ำ, ตอบเป็น JSON เท่านั้น — ที่จำแนก intent, ตัดสินใจว่าจะเรียกใช้ specialist
agent ตัวไหนในสี่ตัว (financials, news, calc, ratios), และดึง ticker ออกมา ถ้า JSON นั้นผิด
รูปแบบ ระบบไม่พัง แต่จะ fallback ไปใช้ keyword heuristic แทน

ถัดมาคือโหนด **gates** ที่ผมไม่ไว้ใจ planner LLM เต็มที่: ถ้าผู้ใช้เอ่ยชื่อกลุ่มอย่าง 'FAANG'
หรือ 'MAG7' ผมจะ override ticker ที่ LLM เดามาด้วยรายการ manifest มาตรฐาน — ผมเคยจับได้ว่า
planner ตกหล่น META กับ NVDA แล้ว hallucinate FB/BABA ขึ้นมาแทน จากนั้นทุก ticker จะถูกตรวจสอบ
กับรายชื่อ SEC filer จริง ticker ที่ตายแล้วหรือ hallucinate ขึ้นมาจะถูกตัดทิ้งก่อนที่ agent
ตัวไหนจะเปลือง token กับมัน

จากนั้นมันกระจายงาน — LangGraph's `Send` API จะส่งงานหนึ่งโหนดต่อหนึ่ง agent ที่วางแผนไว้ ให้รัน
พร้อมกัน แล้วโหนด **collect** จะรวมผลลัพธ์ผ่าน state reducer แทนที่จะจัดการ thread-pool ด้วยมือ
แต่ละ agent มี tool list ของตัวเองและรัน guarded tool-calling loop ร่วมกันโดยมีงบ token และ
จำนวนรอบของตัวเอง

ผลลัพธ์เหล่านั้นถูกต่อกันเป็น context แล้วส่งให้ **synthesis** LLM ที่ถูกสั่งให้ตอบจาก context
นั้น *เท่านั้น* จากนั้น — และนี่คือส่วนที่ผมภูมิใจที่สุด — **deterministic fidelity verifier**
จะดึงตัวเลขยอดเงิน เปอร์เซ็นต์ และ ratio ทุกตัวออกจากคำตอบนั้นด้วย regex ผูกแต่ละตัวเข้ากับปี
งบการเงิน แล้วเช็คกับ raw tool call output ถ้าตัวเลขไหนสืบย้อนกลับไม่ได้ โมเดลจะได้ prompt

## 2. "จัดการความล้มเหลวของ tool-calling หรือ LLM schema parsing error ใน LangGraph ยังไง"

**คำตอบที่พูดออกเสียง:**
"มีสามเลเยอร์แยกกัน เพราะผมไม่ไว้ใจให้เลเยอร์ไหนเลเยอร์เดียวจับทุกอย่างได้

อย่างแรก ผลลัพธ์ JSON ของ planner: ผม regex ดึงบล็อก `{...}` แรกออกมาแล้ว `json.loads` ถ้ามัน
throw error — JSON ผิดรูปแบบ หรือโมเดลห่อมันด้วยข้อความอื่น — ผมไม่ retry LLM แต่จะ fallback ไป
ใช้ keyword heuristic ราคาถูกที่อย่างน้อยก็เลือก agent ที่พอเป็นเหตุเป็นผลได้ ทำให้ planner call
ที่แย่ทำให้คุณภาพการ routing แย่ลง แทนที่จะทำให้เทิร์นพังทั้งหมด

อย่างที่สอง argument ของแต่ละ tool call: field `arguments` ของแต่ละ tool call เป็น JSON และถ้า
parse ไม่ได้ ผมไม่ทำให้ loop พัง — ผม default เป็น dict ว่าง ซึ่งแปลว่า call นั้นจะกลับมาเป็น
error string ระดับ tool ปกติที่ agent สามารถตอบสนองและลองใหม่ด้วยวิธีอื่นได้

อย่างที่สาม — และผมคิดว่าอันนี้น่าสนใจกว่า — ผมไม่ได้แค่จัดการ tool call ที่ *ผิดรูปแบบ* เท่านั้น
ผมมีเลเยอร์ Pydantic อยู่ใต้ทุกอย่างที่ tool *สำเร็จ* แล้วคืนค่ามา แถวข้อมูลงบการเงินที่ parse
มาแล้วต้องผ่าน validator ที่ปฏิเสธค่าที่ไม่ finite, ค่าที่เกินขอบเขตความสมเหตุสมผล, gross margin
เกิน 100%, หรืองบดุลที่สินทรัพย์ไม่เท่ากับหนี้สินบวกส่วนของผู้ถือหุ้น มันมาจากบั๊กจริง — ผมเคยมี
unit-scale error ที่ทำให้ gross margin ของ Microsoft ขึ้นเป็น 220% หลักการที่ผมยึดถือ: LLM ไม่
ควรต้อง *พิมพ์* ตัวเลขให้ถูกต้องเอง และเลเยอร์ข้อมูลไม่ควรถูกปล่อยให้ *เก็บ* ค่าที่เป็นไปไม่ได้
แถวที่ผิดจะถูกล็อกไว้แล้วทิ้ง ไม่ใช่เก็บไว้แบบเงียบ ๆ

ที่ระดับ orchestrator แต่ละ agent node ถูกครอบด้วย try/except — ถ้า agent throw อะไรก็ตาม ผม
จะล็อกมันไว้ในไฟล์ failure log ที่จะกลายเป็นวัตถุดิบสำหรับ regression test ใหม่ แล้ว node จะคืน
ผลลัพธ์ว่าง เพราะ agent รันเป็นโหนดอิสระที่ dispatch ด้วย `Send` การที่ agent หนึ่งล้มเหลวจึงไม่
ทำให้ตัวอื่นล้มไปด้วย"

**ถ้าถูกซักต่อ / รายละเอียดสำรอง:**
- `_parse_plan` (`orchestrator.py:64-70`) จะ raise `ValueError` ถ้า JSON ที่ parse ได้ไม่ใช่
  dict ซึ่งจะเข้า except branch เดียวกับ `json.JSONDecodeError`
- `_is_error_result` (`agents/_tooling.py:39-44`) เป็น string-prefix heuristic ราคาถูก
  (`error`, `no `, `could not`, `unable`, `unknown tool`) ที่ป้อนให้ no-progress guardrail —
  ตั้งใจให้มันโง่และเร็ว แทนที่จะเป็น LLM call อีกตัวมาตัดสินผลลัพธ์
- `tools/schemas.py`: `StatementRow`, `MarginRow`, `BalanceSheetIdentity` — การเช็คงบดุลมี
  เส้นทางหลักที่แข็งแรง (บรรทัด grand-total ซึ่งครอบคลุม mezzanine/NCI โดยธรรมชาติ) และมี
  fallback ที่ระมัดระวัง ซึ่งจะ *เชื่อ* ก็ต่อเมื่อผลลัพธ์ตรงกันเท่านั้น ไม่มีวัน false-flag เพราะ
  บริษัทจริงบางแห่ง (LCID, PLUG) มีงบดุลที่ไม่ผ่านการเช็คแบบสองกลุ่มธรรมดาด้วยเหตุผลที่ถูกต้อง

## 3. "ถ้า agent ติดอยู่ในลูป tool-calling ไม่รู้จบ ระบบของคุณกู้คืนยังไง"

## 5. "ทำไมต้องใช้สถาปัตยกรรม multi-agent แทนที่จะเป็น LLM ตัวเดียวที่มี prompt ยาวและมี tools ทั้งหมด"

อย่างที่สี่ ขอบเขตความเสียหาย guardrail ของแต่ละ agent — เพดาน 8 รอบ, งบ token 30k — ถูกจำกัด

agent อื่นเสียหาย

อย่างที่ห้า มันคือสิ่งที่ทำให้การตรวจสอบ fidelity เป็นไปได้ตั้งแต่แรก เพราะ tool call ของแต่ละ

## 6. "ทำไมต้องใช้ LangGraph โดยเฉพาะ — แทนที่จะเป็น LangChain หรือเขียนโค้ด Python ธรรมดา"

**คำตอบที่พูดออกเสียง:**
"มีสองคำถามซ้อนอยู่ในนี้ ขอตอบทีละอย่าง — และผมอยากพูดตรง ๆ ก่อนว่าส่วนใหญ่ *สามารถ* เขียนด้วย
Python ธรรมดาได้โดยไม่ยากเท่าไหร่ ผมจะไม่แสร้งทำเป็นอย่างอื่น

การกระจายงานแบบ dynamic — `asyncio.gather` กับ list ที่รู้ตอน runtime ทำได้ในบรรทัดเดียว การ
merge ผลลัพธ์ที่รันพร้อมกัน — เติม dict ตอน future เสร็จก็แค่ห้าบรรทัด logic การ retry/escalation
— ฟังก์ชัน `if`/`elif` ไม่กี่ตัวก็ทำงานเดียวกันได้ ไม่มีอะไรในนี้พิเศษเลย และผมไม่คิดว่า 'ทำแบบนี้
ไม่ได้ถ้าไม่มี framework' เป็นข้ออ้างที่ซื่อสัตย์สำหรับสามอย่างนี้

ส่วนเดียวที่สร้างเองให้ดีจริง ๆ แล้วแพงคือการ resume เมื่อระบบล่มกลางเทิร์น นั่นหมายถึงการ
serialize state ที่ไม่แน่นอนลง database จริงอย่างถูกต้องหลังทุกขั้นตอน ผูกกับ session มี logic
resume แบบ idempotent ที่ข้ามงานที่เสร็จแล้ว จัดการได้ถูกต้องแม้เขียนไม่สมบูรณ์หรือมีการเข้าถึง
พร้อมกัน นั่นคืองาน persistence-layer จริงที่มี edge case เยอะมาก — ไม่ใช่แค่ for-loop — และ
checkpointer ของ LangGraph ให้สิ่งนั้นกับผม ทั้ง Postgres ตอน production และ SQLite ตอนรันใน
เครื่อง แค่เขียนไม่กี่บรรทัดก็ต่อได้ นี่คือข้ออ้างเดียวที่ผมจะยืนยันจริง ๆ ว่า 'สร้างเองแบบถูก ๆ
ไม่ได้'

นอกเหนือจากส่วนนั้น เหตุผลที่ซื่อสัตย์ที่สุดที่ผมใช้ framework กับส่วนที่เหลือคือเรื่องการดูแล
รักษาระบบเมื่อมันโตขึ้น ไม่ใช่ความสามารถดิบ ๆ ที่ 11 โหนดพร้อมเส้นทาง retry แบบมีเงื่อนไขหลาย
เส้น เวอร์ชันที่เขียนเองจะสะสมกลายเป็น conditional ที่ซ้อนกันคอยเช็ค flag ที่ตั้งไว้จากฟังก์ชัน
ก่อนหน้าสามชั้น — นั่นเป็น failure mode จริงและพบบ่อยของโค้ด orchestration ไม่ใช่แค่สมมติฐาน
โมเดล graph ทำให้ทุกการตัดสินใจ routing เป็นฟังก์ชัน pure ขนาดเล็กที่ทดสอบแยกได้ —
`test_graph_routes.py` เทสต์ทุกตัวโดยไม่ต้องเรียก LLM จริงเลยสักครั้ง — และรูปทรงทั้งหมดยังคง
มองเห็นได้ไม่ว่าจะเพิ่มโหนดกี่ตัวในอนาคต แผนภาพสถาปัตยกรรมใน README ถูกสร้างขึ้นตรงจาก compiled
graph object เลย จึงไม่มีทางหลุดไม่ตรงกับโค้ดจริง วิศวกรที่มีวินัยเขียนโค้ดเองให้เป็นรูปทรง
เดียวกันนี้ได้ — framework แค่ทำให้มันเป็นค่า default แทนที่จะเป็นสิ่งที่ต้องคอยจำไว้บังคับใช้
เองทุกครั้งที่แตะโค้ด

ส่วนเรื่อง LangChain โดยเฉพาะ — โปรเจกต์นี้แทบไม่ได้ใช้มันเลย ไม่มี `AgentExecutor` ไม่มี LCEL
chain ไม่มี `Tool` wrapper class; agent เรียก client ที่เข้ากันได้กับ OpenAI โดยตรง และ parse
tool call เองใน loop ที่ใช้ร่วมกัน LangGraph เป็น library แยกต่างหากระดับล่างสำหรับ execute
graph ที่บังเอิญมาจาก ecosystem เดียวกัน — ผมใช้มันเพราะมันเหมาะกับ 'โหนด, conditional edge,
parallel fan-out, persisted state' ไม่ใช่เพราะผมซื้อ stack ของ LangChain ทั้งชุด"

**ถ้าถูกซักต่ออีก — 'แต่เขียนทั้งหมดนี้ด้วย Python ธรรมดาไม่ได้เหรอ':**
"ได้ พูดตรง ๆ ประมาณ 90% เลย — และถ้านี่เป็น pipeline ที่เล็กหรือเป็นเส้นตรงมากกว่านี้ ผมคงทำ
แบบนั้นจริง ๆ ผมตั้งใจกำหนดขอบเขตโปรเจกต์นี้ให้รวมส่วนที่ไม่ปรากฏจนกว่าจะต้องใช้จริงตอนขยาย

ประเภทนั้นโดยใช้เครื่องมือที่สร้างมาเพื่อสิ่งนี้ แทนที่จะหลีกเลี่ยงมันหรือสร้าง persistence

# Sections 1–4 — คำถามตามหลังที่สำคัญ

## "ตัดสินใจยังไงว่า agent ควรวนกลับหรือควรจบการทำงาน"

**คำตอบที่พูดออกเสียง:**
"มีลูปสองแบบที่ต่างกัน และผมใช้กฎการตัดสินใจต่างกันโดยตั้งใจ

ภายในเทิร์นของ tool-calling ของ agent ตัวเดียว มันง่าย: วนต่อไปตราบใดที่โมเดลยังขอ tool อยู่และ
ยังไม่มี guardrail ทำงาน หยุดทันทีที่มันคืนเนื้อหาธรรมดา หรือทันทีที่ guardrail (เพดานจำนวนรอบ,
งบ token, no-progress) ทำงาน — และตอนที่ guardrail ทำงาน ผมจะบังคับให้ตอบครั้งสุดท้ายแบบไม่มี
tool เพื่อให้มันยังจบด้วยอะไรบางอย่าง

ที่ระดับ graph การตัดสินใจวนกลับขึ้นอยู่กับ *คุณภาพของหลักฐาน* ไม่ใช่ตัวนับ หลัง synthesis
ถ้า agent คืนอะไรมาแทบไม่ได้เลย หรือคำตอบอ่านแล้วดูไม่แน่ใจ ผมจะไปที่ web fallback ถ้ามี
หลักฐานจาก tool จริง ผมจะรัน fidelity check เฉพาะ HARD mismatch เท่านั้น — ตัวเลขที่ไม่มีอยู่
สำหรับ *ปีไหนเลยที่ดึงมาได้* ซึ่งเป็นสัญญาณที่หนักแน่นที่สุดว่าโมเดลดึงมาจากข้อมูลตอนเทรน ไม่ใช่
จากเอกสารที่ดึงมา — จะส่งไป self-critique อีกครั้ง mismatch ที่เบากว่า อย่างตัวเลขจริงแต่ผูกปี
ผิด จะถูกล็อกไว้แต่ไม่ trigger การ re-prompt เพราะผมเคยลองแล้วมันแค่สร้างความปั่นป่วนโดยไม่ได้
เพิ่มความแม่นยำจริง

และที่สำคัญคือ self-critique ไม่มีวันวนกลับไปที่ fidelity check อีก — edge นั้นไม่มีอยู่ใน
graph มันจะไปที่ web escalation ถ้าตัวเลขที่ผิดยังอยู่หลังจากนั้น และ web escalation จะ finalize
เสมอ ดังนั้นความลึกของการ retry ถูกจำกัดด้วยรูปทรงของ graph ไม่ใช่ตัวนับ runtime — ไม่มีทางไหน
ผ่าน graph นี้ที่จะวนไม่รู้จบได้เลย ตามโครงสร้างที่ออกแบบไว้"

## "จัดโครงสร้าง Pydantic schema หรือ function signature ยังไงให้ agent ไม่เรียก tool ผิด"

**คำตอบที่พูดออกเสียง:**
"มีหลายเลเยอร์ ส่วนใหญ่อยู่ก่อนถึง LLM มากกว่าที่จะพยายามเขียน prompt ให้ครอบคลุมทุกอย่าง

แต่ละ agent ในสี่ตัวมี tool list ของตัวเอง — tool ของ financials มองไม่เห็นจาก news agent
และในทางกลับกัน ทำให้โมเดลเลือกจาก function ที่เกี่ยวข้องแค่ 4-6 ตัว ไม่ใช่ยี่สิบตัว ผมยังบังคับ
`tool_choice='required'` ในรอบแรกด้วย เพื่อไม่ให้เกิดความกำกวมว่ามันตั้งใจเรียก tool หรือไม่

สำหรับ argument, JSON ที่ผิดรูปแบบใน tool call ไม่ทำให้อะไรพัง — มัน default เป็น dict ว่าง
และ tool เองจะคืน error string ปกติ ซึ่งจะป้อนเข้า no-progress guardrail ถ้ามันเกิดขึ้นซ้ำ ๆ

ส่วนที่ผมอยากเน้นว่าเป็นการออกแบบที่น่าสนใจกว่า: ผมไม่ได้พึ่งแค่ input schema ของ tool อย่าง
เดียวเพื่อกันข้อมูลแย่ ๆ ออกไป — มีเลเยอร์ Pydantic ที่ *ตรวจสิ่งที่ tool คืนมา* ก่อนที่มันจะ
กลับเข้าไปใน context ของ LLM อีกครั้ง ดังนั้นแม้แต่ tool ที่ถูกเรียกอย่างถูกต้องแต่คืนผลลัพธ์ที่
parse ผิด — NaN, margin ที่เป็นไปไม่ได้, งบดุลที่ไม่สมดุล — ก็จะถูกจับและทิ้งตรงนั้น ไม่ถูกส่งต่อ
ให้โมเดลนำไปใช้เหตุผลแล้วเผลอเชื่อ

และสำหรับ failure mode เฉพาะแบบ 'ticker ผิด' ไม่ใช่ 'tool ผิด' ผมไม่ปล่อยให้โมเดลพิมพ์
ticker symbol เข้าสู่ pipeline เองเลย มี deterministic resolution ladder (จับคู่ตรงตัว, ตาราง
alias, fuzzy match, ปฏิเสธเมื่อกำกวม, semantic search) อยู่ด้านหน้า และมี validation gate ที่ตัด
ticker ใด ๆ ที่ไม่ใช่ SEC filer ที่ยังจดทะเบียนอยู่จริง ก่อนที่ agent จะรันเลยด้วยซ้ำ"

## "เกิดอะไรขึ้นเมื่อ external API (อย่าง SEC EDGAR, DuckDB, หรือ web search) ล้มเหลว, timeout, หรือคืนผลลัพธ์ว่างเปล่า"

ควบคุม* ไม่มีวันทำให้ทั้งเทิร์นล่มไปแบบเงียบ ๆ

ที่ระดับ tool-loop, error หรือผลลัพธ์ว่างจาก SEC/yfinance/news จะกลับมาเป็น string ปกติ ถูก
ตรวจจับด้วย prefix check ราคาถูก แล้วป้อนเข้า no-progress guardrail — สามครั้งติดกันแล้ว loop
จะหยุดและสรุปแทนที่จะยิง API ที่ตายแล้วให้ครบ 8 รอบ

ที่ระดับ orchestrator, แต่ละ agent node ถูกครอบด้วย try/except; exception จะถูกล็อกไว้ในไฟล์
failure — ซึ่งเป็นวิธีที่ regression test ใหม่ถูกสร้างขึ้นด้วย — แล้ว node จะคืนค่าว่างเปล่า
เพราะ agent เป็นโหนดอิสระที่ dispatch ด้วย `Send` การที่ตัวหนึ่ง throw error จึงไม่บล็อกหรือทำให้
ตัวอื่นเสียหาย

การตรวจสอบ ticker ล้มเหลวแบบเปิดโดยตั้งใจ: ถ้ารายชื่อ ticker ของ SEC เองโหลดไม่ได้ — เช่น
EDGAR ล่ม — ผมไม่ปฏิเสธ ticker ทุกตัวในคำถาม แต่จะถือว่าทุกตัวถูกต้องแทนที่จะทำลายทั้งเทิร์นเพราะ
ข้อมูลอ้างอิงล่มชั่วคราว แนวคิดเดียวกันสำหรับ tier semantic ในการ resolve ticker — ถ้า Qdrant
เข้าไม่ถึง tier นั้นจะคืน 'ไม่เจอ' แล้ว ladder ก็ไหลผ่านต่อไป ไม่ propagate exception ออกไป

ที่ระดับบนสุด ถ้า agent ทั้งหมดรวมกันคืนอะไรมาไม่ได้เลย หรือคำตอบที่สังเคราะห์แล้วอ่านดูไม่แน่ใจ
มันจะ route ไปที่ web search fallback ถ้า Tavily ไม่ได้ตั้งค่าไว้หรือเกิด error ฟังก์ชันนั้นจะ
log คำเตือนแล้วคืนค่าว่าง — ซึ่ง graph จะถือว่าเป็น no-op ไม่ใช่การพัง — แล้วไหลไปสู่ทางเลือก
สุดท้าย: คำตอบจะออกไปพร้อมข้อความชัดเจนว่า 'ตัวเลขเหล่านี้ยืนยันไม่ได้' ดังนั้น failure mode ที่
แย่ที่สุดของ external dependency ตัวไหนก็ตามคือคำเตือนที่มองเห็นได้บนคำตอบ ไม่มีวัน stack trace
และไม่มีวัน — ซึ่งเป็นคุณสมบัติที่ผมใส่ใจจริง ๆ — ตัวเลขที่ผิดแบบมั่นใจถูกส่งออกไปแบบเงียบ ๆ

และอีกระดับเหนือทั้งหมดนั้น: ถ้า *ตัว process เอง* ตายกลางเทิร์น ไม่ใช่แค่ API call เดียว
LangGraph checkpointer — Postgres ตอน production, SQLite ตอนรันในเครื่อง — มี state ของเทิร์น
เก็บไว้ต่อ thread ดังนั้นมันจะ resume จากโหนดล่าสุดที่เสร็จแล้ว แทนที่จะเริ่มทั้งเทิร์นใหม่"

## Bonus deep-dive — "เล่าให้ฟังว่า guardrail ของ fidelity verifier ทำงานยังไงจริง ๆ" (`tools/fidelity.py`)

นี่คือส่วนที่โดดเด่นที่สุดในโปรเจกต์ ดังนั้นเตรียมใจว่าจะถูกซักลึก มันคือ guardrail แยกกันห้าชั้น
ที่ซ้อนกันอยู่ แต่ละชั้นป้องกัน failure mode ที่ต่างกัน — ไม่ใช่การเช็คก้อนใหญ่ก้อนเดียว

**คำตอบที่พูดออกเสียง:**
"มันคือฟังก์ชัน pure และ deterministic — `verify(answer, tool_blocks)` — ไม่มี LLM อยู่ใน loop
เลย มีห้าอย่างที่ต้องถูกต้องเพื่อให้มันน่าเชื่อถือ

อย่างแรก การดึงข้อมูลต้องหลีกเลี่ยงการนับซ้ำ string อย่าง `$391,035M` ในทางทฤษฎีอาจตรงกับ
pattern ตัวเลขได้มากกว่าหนึ่งแบบ ผมเลยดึงตามลำดับความสำคัญที่เข้มงวด — เงินแบบมีคำต่อท้าย
ก่อน จากนั้นเงินที่สะกดเป็นคำอย่าง '391 billion' จากนั้นดอลลาร์ธรรมดา จากนั้นเปอร์เซ็นต์
จากนั้น ratio — และเมื่อช่วงข้อความหนึ่งถูกจับโดย match ที่มีความสำคัญสูงกว่าแล้ว จะไม่มี match
ที่สำคัญน้อยกว่ามาจับซ้ำในช่วงนั้นได้อีก มีการป้องกันระดับ regex ที่ทำหน้าที่ซ้ำกันด้วย: pattern
ดอลลาร์ธรรมดามี negative lookahead ที่ปฏิเสธการ match ถ้าตัวเลขตามด้วยคำต่อท้ายขนาดหรือ
เครื่องหมายเปอร์เซ็นต์ทันที

อย่างที่สอง ผมดึงเฉพาะตัวเลขที่ *มีหน่วย* เท่านั้น — สกุลเงิน, เปอร์เซ็นต์, ratio จำนวนเต็ม
ธรรมดา, การนับ, และปีสี่หลัก ไม่มีวันเป็นตัวเลือกเลย นี่คือแนวป้องกัน false-positive หลัก —
ไม่งั้นอะไรอย่าง 'รายงานในปี 2024' จะถูกตีความว่าเป็นตัวเลขที่ไม่มีที่มา

อย่างที่สาม ทุกตัวเลขจะถูกผูกเข้ากับปีงบการเงิน และข้อความอาจนำเสนอปีได้สองแบบที่ต้องใช้ logic
ต่างกัน การเขียนแบบสลับกัน — '$391B ในปี FY2024 และ $383B ในปี FY2023' — จะผูกแต่ละตัวเลขกับ
token ปีที่ใกล้ที่สุด แต่การเขียนแบบแจกแจง — 'FY2023, FY2024, FY2025... คือ $X, $Y, $Z ตามลำดับ'
— จะทำให้ตรรกะนั้นพัง: การใช้ปีที่ใกล้ที่สุดจะผูกทั้งสามค่าเข้ากับปีสุดท้ายที่ระบุ ผมเลยมี
ขั้นตอนแยกที่ตรวจตำแหน่ง ถ้าจำนวนปี N ตัวอยู่หน้าค่าประเภทเดียวกัน N ค่า มันจะผูกกันตามลำดับ
ตำแหน่งแทน

อย่างที่สี่ การจับคู่ใช้ tolerance แบบสัมพัทธ์ ไม่ใช่ความเท่ากันทุกตัว — หนึ่งเปอร์เซ็นต์ —
เพราะการที่โมเดลเขียน '391,035M' ใหม่เป็น '$391.0B' คือการปรับรูปแบบที่ถูกต้อง ไม่ใช่การ
แต่งตัวเลขขึ้นมาเอง และการจับคู่แบบเป๊ะจะ false-flag ตลอดเวลา

อย่างที่ห้า และนี่คือส่วนที่ขับเคลื่อนพฤติกรรมจริง ๆ: mismatch จะถูกจัดประเภทเป็น hard หรือ soft
และมีแค่ hard mismatch เท่านั้นที่มีค่าใช้จ่ายสูง ตัวเลขที่ตรงกับข้อมูล tool สำหรับปีอื่นที่ดึงมา
ได้ *บางปี* คือ soft — น่าจะเป็นการติด label ผิด แค่ล็อกแล้วปล่อยไว้ ไม่ re-prompt เพราะผมเคย
ลอง re-prompt กับกรณีนี้แล้วมันสร้างความปั่นป่วนโดยไม่เพิ่มความแม่นยำ ตัวเลขที่ไม่ตรงกับปีไหน
ที่ดึงมาได้เลยคือ hard — นั่นคือสัญญาณที่หนักแน่นที่สุดว่ามันมาจากข้อมูลตอนเทรนของโมเดล ไม่ใช่
จากเอกสารที่ดึงมาจริง และนั่นคือสิ่งที่ trigger การ retry แบบ self-critique

มีอีกชั้นหนึ่งซ้อนอยู่บนนั้นที่ผมพอใจเป็นพิเศษ: แม้ *ค่า* ของตัวเลขจะบังเอิญตรงกับปีอื่นที่ดึงมา
ได้จริง — สมมติรายได้ของบริษัทเมื่อสองปีก่อนบังเอิญใกล้เคียงกับปีที่แล้วภายในหนึ่งเปอร์เซ็นต์ —
ถ้าตัวเลขนั้นถูกระบุ label เป็นปีที่ไม่เคยถูกดึงมาในเทิร์นนี้เลย มันจะยังถูกบังคับเป็น hard อยู่ดี
ความตรงกันของค่าโดยบังเอิญข้ามปีไม่ได้ทำให้การอ้างปีที่เจาะจงนั้นมีที่มาจริง นั่นคือกลไกที่จับ
บั๊กจริงได้ตอนใช้งานสด: โมเดลตอบด้วยรายได้ของ Microsoft ปี FY2020 และ FY2019 — ตัวเลขถูกต้อง
มาจากข้อมูลตอนเทรนตรง ๆ — ทั้งที่มีแค่ FY2023 ถึง FY2025 เท่านั้นที่ถูกดึงมาจริงในเทิร์นนั้น
ตัว verifier จับทั้งสองตัวได้ self-critique เขียนคำตอบใหม่ และผู้ใช้ไม่เคยเห็นมันเลย"

  `year not in grounded_years` ที่บังคับให้เป็น hard แม้ค่าจะตรงกันโดยบังเอิญ เงื่อนไขนั้นเองก็
  มีการป้องกัน — มันทำงานเฉพาะเมื่อ `grounded_years` ไม่ว่างเปล่า ดังนั้น tool response ที่ไม่มี

- ฟังก์ชันนี้ **pure และ flag-only** — มันไม่เคยแก้ไข `answer` การแยกส่วนแบบนี้เองก็เป็นการ

  และมันทดสอบแยกได้โดยไม่ต้องเรียก LLM เลย
- ข้อจำกัดที่ควรยอมรับตรง ๆ ถ้าถูกถาม: มันใช้ regex เป็นฐาน ดังนั้นมันจะจับตัวเลขที่แต่งขึ้นมาเอง
  แบบเขียนเป็นข้อความล้วน ๆ ไม่มี token หน่วยไม่ได้ และมันเช็คได้แค่ตัวเลขเท่านั้น — มันไม่มีทาง
  ตรวจ claim เชิงคุณภาพ ("margin กำลังดีขึ้น") เทียบกับข้อมูลต้นฉบับได้

# Section 6 — คำถามที่จะถาม Mr. Dor Haim ตอนท้าย

คำถามพวกนี้ไม่ใช่แค่พิธีการ — ฟังคำตอบจริง ๆ แล้วปล่อยให้มันนำไปสู่คำถามต่อยอด สำหรับแต่ละข้อ
มีคำอธิบายสั้น ๆ ว่า *ทำไมมันเป็นคำถามที่ดี* และวิธีโยงกลับไปที่โปรเจกต์ของคุณถ้าบทสนทนาชะงัก

### "สถาปัตยกรรมหลักที่ใช้กับ agent ที่นี่ตอนนี้คือแบบไหน — autonomous loop agent, strictly routed graph workflow, หรือแบบผสม"

ทำไมต้องถาม: มันจะบอกว่าระบบ production ของเขาเน้นความยืดหยุ่น (autonomous ReAct-style loop)
หรือความคาดเดาได้ (graph ที่มี edge ตายตัวแบบของคุณ) ระบบ production จริงมักจะเป็นแบบผสม —
โครงสร้างที่ route ไว้พร้อมลูปที่จำกัดอยู่ในหนึ่งหรือสองโหนด ซึ่งตรงกับรูปทรงของคุณเองเป๊ะ ๆ
(tool loop ของ agent ที่ถูกจำกัดอยู่ภายใน graph ที่ route ไว้) ถ้าเขาตอบว่า "ส่วนใหญ่เป็น
autonomous" คำถามต่อยอดที่ดีคือถามว่าเขาจำกัด runaway loop ยังไงในทางปฏิบัติ — คุณมีคำตอบที่
เจาะจงมาเทียบกันได้จริง (การออกแบบ guardrail สี่ชั้น) แทนที่จะแค่พยักหน้าตาม

### "ทีมจัดการเรื่อง agent evaluation และ regression testing ยังไงเมื่อ deploy prompt/model update เข้า production"

ทำไมต้องถาม: นี่คือคำถามที่ผู้สมัครส่วนใหญ่ *ตอบต่อไม่ได้จริงจัง* เพราะพวกเขาไม่เคยสร้างกล้ามเนื้อ
นี้ขึ้นมาเอง แต่คุณมี — offline model-comparison harness, นโยบาย regression ที่ตรึงด้วยข้อมูล
จริง, และ loop การให้คะแนนผ่าน Langfuse trace ฟังดูว่าเขามีอะไรที่ทำหน้าที่แบบเดียวกับ
fidelity-score-on-every-trace ของคุณไหม: สัญญาณจาก production ที่ถูกเช็คต่อเนื่อง ไม่ใช่แค่
test suite ก่อน deploy ถ้าเขาไม่มี นี่คือช่องว่างที่ควรพูดถึงอย่างตรงไปตรงมาว่าคุณอยากช่วยปิด
ช่องว่างนั้น

### "use case หลักที่กำลังสร้าง AI agent ที่นี่คืออะไร — แบบ customer-facing (ค้นหา/แชทเรื่อง property), แบบภายใน (วิเคราะห์เอกสาร/สัญญาเช่า, คัดกรอง lead) หรือทั้งสองแบบ"

## จุดอ่อนบางอย่างที่ควรพร้อมยอมรับตรง ๆ

ผู้สัมภาษณ์มักจะซักหา self-awareness พอ ๆ กับความสามารถ ถ้าถูกถามว่า "จุดที่อ่อนที่สุดของ
ระบบนี้คืออะไร" นี่คือคำตอบจริงที่ยืนยันได้ — ไม่ใช่คำตอบที่ทำให้บทสนทนาจบ:

- **fidelity verifier ใช้ regex เป็นฐาน** ปรับแต่งมาสำหรับ pattern ของสกุลเงิน/เปอร์เซ็นต์/ratio
  — มันจะจับตัวเลขที่แต่งขึ้นแบบเขียนเป็นข้อความล้วน ๆ ไม่มีหน่วย ("ประมาณสี่แสนล้านดอลลาร์"
  โดยไม่มี `$`/`B`) ไม่ได้ และมันไม่ได้ตรวจ claim เชิงคุณภาพเลย ตรวจได้แค่ตัวเลขเท่านั้น
- **การ override ด้วย group-manifest (MAG7/FAANG) เป็นรายการตายตัวที่ hardcode ไว้** ไม่ใช่
  ทางแก้แบบทั่วไป — มันแก้ failure mode เฉพาะของ planner แต่ไม่ครอบคลุมชื่อกลุ่มอื่น ๆ ที่ planner
  อาจจะประดิษฐ์ขึ้นมาเอง
- **self-critique ตั้งใจให้ทำแค่รอบเดียว** — เป็นการจำกัดที่ตั้งใจเพื่อกัน retry ไม่รู้จบ แต่มันก็
  หมายความว่า hallucination ที่ดื้อรั้นซึ่งรอดจาก re-prompt หนึ่งครั้งจะถูกส่งตรงไป web
  escalation แทนที่จะได้ลองแก้ภายในอีกครั้ง
- **ไม่มี offline regression suite สำหรับ fidelity โดยเฉพาะ** — มันถูกเช็คแบบสดต่อเทิร์นและให้
  คะแนนเข้า Langfuse แต่ไม่มี fixed benchmark ของ "prompt ที่รู้ว่ายาก" รันใน CI แบบเดียวกับที่
  eval harness ของ routing/tool-selection ทำ เป็นคำตอบที่ดีสำหรับ "จะทำอะไรต่อไป" แบบตรงไปตรงมา
